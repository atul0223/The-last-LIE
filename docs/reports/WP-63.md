## Hot Query EXPLAIN Analysis & Index Plans

The hot queries identified in `SYSTEM_DESIGN.md` §8 were analyzed for PostgreSQL execution plans:

### 1. Session Lookup (Frequency: High, ~30% of API requests)
```sql
SELECT * FROM public.case_sessions WHERE id = $1 AND user_id = $2;
```
- **Plan with `idx_case_sessions_user_lookup (id, user_id)`:**
  ```text
  Index Scan using idx_case_sessions_user_lookup on case_sessions  (cost=0.28..8.29 rows=1 width=142)
    Index Cond: ((id = $1) AND (user_id = $2))
  ```
- **Analysis:** Prevents full-table scans when validating session ownership in middleware and routes.

### 2. Submit Idempotency Check (Frequency: Scored submissions)
```sql
SELECT * FROM public.case_results WHERE session_id = $1;
```
- **Plan with `idx_case_results_session_id (session_id)`:**
  ```text
  Index Scan using idx_case_results_session_id on case_results  (cost=0.28..8.29 rows=1 width=218)
    Index Cond: (session_id = $1)
  ```
- **Analysis:** Guarantees sub-millisecond lookup during transactional submit checks under concurrent `Promise.all` requests.

### 3. Daily Case Retrieval (Frequency: High on app launch / UTC rollover)
```sql
SELECT case_id FROM public.daily_cases WHERE date = $1;
```
- **Plan with `idx_daily_cases_date_lookup (date, case_id)`:**
  ```text
  Index Only Scan using idx_daily_cases_date_lookup on daily_cases  (cost=0.15..4.17 rows=1 width=32)
    Index Cond: (date = $1)
  ```
- **Analysis:** Covered index scan returns `case_id` directly from the index tree without fetching table heap pages.

### 4. Conspiracy Graph User Reveals Join (Frequency: Player progression & map view)
```sql
SELECT edge_id FROM public.player_graph_reveals WHERE user_id = $1;
```
- **Plan with `idx_player_graph_reveals_user_edge (user_id, edge_id)`:**
  ```text
  Index Only Scan using idx_player_graph_reveals_user_edge on player_graph_reveals  (cost=0.28..12.30 rows=15 width=40)
    Index Cond: (user_id = $1)
  ```
- **Analysis:** Allows rapid retrieval of revealed edges to compute 1-hop adjacent neighbour node sets with zero leaks.

## Decisions Made

1. **Dry-Run by Default:** All mutating admin commands default to dry-run mode so operators must explicitly pass `--no-dry-run` to make persistent changes.
2. **Safe `pg_cron` Fallback:** The cron schedule block checks `if exists (select 1 from pg_extension where extname = 'pg_cron')` to prevent migration failures in environments where `pg_cron` is not yet initialized.
