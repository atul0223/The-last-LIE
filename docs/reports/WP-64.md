# Definition of Done Report: WP-64 Push Token Path & RLS Lockdown

## Summary
- **Additive Push Token Contract:** Extended `@lastlie/api-contract` with `UnregisterPushTokenRequestSchema` and `UnregisterPushTokenResponseSchema` for `DELETE /push/token`, and added `unregisterPushToken?` to `ApiClient`.
- **Strict RLS Lockdown:** Created migration `supabase/migrations/20261109000000_push_tokens_tighten_rls.sql` dropping all previous client policies (`push_tokens_own_select`, `push_tokens_own_insert`, `push_tokens_own_update`, `push_tokens_own_delete`) and revoking all client permissions (`select`, `insert`, `update`, `delete`) from `anon` and `authenticated`.
- **Sole Write & Read Path:** The Edge Function API (running under the service role) is now the single authoritative path to register (`POST /push/token`) and unregister (`DELETE /push/token`) push tokens. Clients can neither read nor write to the table directly.
- **Repository & Route Implementation:** Added `deletePushToken(userId, token?)` to `Repository`, implemented in `InMemoryRepository` and `PostgresRepository`, and wired up `DELETE /token` inside `createPushRouter`.
- **Verification:** Unit and integration tests in `supabase/tests/account.test.ts` verify successful registration, deregistration, 401 unauthenticated enforcement, and zero leak scans.

## Decisions Made

1. **Service Role Brokered Access:** Revoking all direct client access (`read none, write none`) ensures that malicious clients cannot scrape push tokens or inject spam tokens across user accounts.
2. **Flexible Deregistration:** `DELETE /push/token` accepts an optional `token` in the body or query parameter; if omitted, it clears all push tokens registered for that user (e.g. on global sign out or account cleanup).
