# WP-43 Definition of Done Report — RemoteGameService

## Summary
- **GameService over API**: Implemented `RemoteGameService` conforming to `GameService` using `FetchApiClient` to communicate with backend REST endpoints (`/sessions`, `/sessions/:id/unlock`, `/sessions/:id/board`, `/sessions/:id/submit`, `/daily`, `/graph`).
- **Contract Schema Validation**: Every API response is validated at runtime against `@lastlie/api-contract` Zod schemas (`CreateSessionResponseSchema`, `UnlockClueResponseSchema`, `SaveBoardResponseSchema`, `SubmitSessionResponseSchema`, etc.), rejecting immediately on schema mismatches with typed `RemoteServiceError`.
- **Error Mapping & Typed Errors**: Implemented `RemoteServiceError` mapping `ApiErrorEnvelope` / `ApiError` with helper flags (`isClientError`, `isServerError`, `isNotFound`, `isConflict`, `isUnauthorized`, `isSchemaMismatch`).
- **TanStack Query Caching & Retries**: Configured `createRemoteQueryClient` with strict retry policies: 4xx client errors are never retried, while network and 5xx server errors retry with exponential backoff up to 3 times.
- **Offline SaveBoard Queue**: Implemented `SaveBoardOfflineQueue` backed by `KeyValueStore` (MMKV / Memory fallback). Last write wins per session. Offline boards queue persistently and flush when back online, purging invalid/closed sessions on 4xx errors.
- **Submit Pending State & Idempotency**: Enforced submission lock per session (`isSubmitting(sessionId)`) preventing concurrent/duplicate submissions, flushing pending offline boards before theory submission.
- **Production Build Guards**: Implemented strict production guards. When running in production (`__DEV__ === false` or `NODE_ENV === 'production'`), `mode` is locked to `'remote'`, attempting to select `'local'` throws an error, and the DEV badge is impossible.
- **Zero Leaks**: All public case and submission payloads pass `deepScan` tests with zero leakage of forbidden keys (`truth`, `claims`, `culpritIds`, `seed`, `keyEvidence`, `liars`, or locked clue text).

## Decisions Made
1. **Queue Purge Policy on 4xx**: When flushing the offline `saveBoard` queue, if the server returns a 4xx error (e.g. 404 session not found or 409 session already submitted), the entry is permanently dequeued. Keeping dead entries would permanently block or corrupt subsequent flush cycles.
2. **Pre-submit Offline Flush**: When submitting a theory (`submit`), `RemoteGameService` attempts to flush any pending offline board for that session first, ensuring the server evaluates the most up-to-date board configuration.
3. **Strict Production Impossibility**: `isProduction()` evaluates both `__DEV__` and `NODE_ENV`. In production, `getServiceConfig()` overrides any configuration to `'remote'`, and `setServiceConfig({ mode: 'local' })` throws an error. `isDevBadgeVisible()` always returns `false`.

## How to Run Maestro Flow in Remote Mode Against Local Supabase

1. **Start Local Supabase Backend**:
   ```bash
   pnpm supabase start
   ```
2. **Set Environment in `apps/mobile/.env.local`**:
   ```bash
   EXPO_PUBLIC_GAME_SERVICE=remote
   # For Android emulator (10.0.2.2 maps to host localhost):
   EXPO_PUBLIC_API_URL=http://10.0.2.2:54321/functions/v1/api
   EXPO_PUBLIC_SUPABASE_URL=http://10.0.2.2:54321
   # For iOS simulator:
   # EXPO_PUBLIC_API_URL=http://localhost:54321/functions/v1/api
   # EXPO_PUBLIC_SUPABASE_URL=http://localhost:54321
   ```
3. **Launch the App on Emulator/Simulator**:
   ```bash
   cd apps/mobile
   npx expo run:android # or npx expo run:ios
   ```
4. **Execute Maestro Flows**:
   ```bash
   maestro test apps/mobile/e2e/case_solve_flow.yaml
   maestro test apps/mobile/e2e/case_fail_flow.yaml
   ```
