# WP-46 Report: Mobile Analytics & Sentry Monitoring

## 1. Summary
- **PostHog & Sentry Integration**: Added `posthog-react-native` and `@sentry/react-native` (installed via Expo CLI for compatibility) committed under dedicated commit `[WP-46] deps: add posthog-react-native and @sentry/react-native`.
- **Strict §11 Event Union**: Implemented `AnalyticsEvent` covering all 13 standard telemetry events (`app_open`, `case_started`, `clue_viewed`, `clue_unlocked`, `board_link_created`, `case_submitted`, `reveal_viewed`, `next_case_tapped`, `challenge_created`, `challenge_opened`, `challenge_completed`, `signup_from_challenge`, `case_reported`). Free-form event names are strictly prohibited.
- **Prop Allow-list & Anti-Leak Validation**: Runtime validation verifies property keys against a strict allow-list, blocking unauthorized properties, PII keys (`email`, `name`, `user`, `secret`), email strings, free text prose (>4 words, >64 chars), and narrative mystery terms.
- **Anonymous Distinct ID & Consent Toggle**: Generated IDs use `anon_<random>_<timestamp>` (never emails or device identifiers). Consent is persisted via MMKV/Memory storage, defaulting to `true` in development (`__DEV__`) and `false` in production. Disabling consent completely silences `track()`.
- **Sentry Telemetry with PII Scrubbing**: Operates as a safe no-op when `EXPO_PUBLIC_SENTRY_DSN` is empty. The `scrubSentryEvent` transformer scrubs user emails, usernames, IP addresses, authorization/cookie headers, sensitive query parameters (`token`, `password`), and email occurrences in breadcrumbs.
- **Provider Wiring**: Minimal root layout wiring wrapped `_layout.tsx` with `<SentryProvider>` and `<AnalyticsProvider>` emitting `app_open`.

## 4. Decisions Made
1. **TypeScript Strictness**: Zero `any` and zero `@ts-ignore` in `src/lib/analytics` and `src/lib/sentry`. Used `Record<string, unknown>` and safe type narrowing for Sentry event scrubbing.
2. **PostHog Session Recording**: Explicitly disabled (`enableSessionRecording: false`) in client initialization to avoid unintended screen captures or DOM recording.
3. **Sentry Provider in `.ts` vs `.tsx`**: Used `React.createElement(React.Fragment, null, children)` in `src/lib/sentry/index.ts` to allow standard `.ts` compilation without JSX syntax issues in headless Node/Vitest environments.

## 5. Requests (Feature Call Sites)
Because feature directories (`features/case/*`, `features/library/*`, `store/useCaseSession.ts`) are owned by other work packages, their call sites should be hooked up by their respective owners using `import { track } from '../lib/analytics'`:

1. **`case_started`**: In `useCaseSession` or `features/case/briefing/index.tsx`:
   ```ts
   track({
     name: 'case_started',
     properties: { caseId, kind: casePublic.kind, difficulty: casePublic.difficulty, mode },
   });
   ```
2. **`clue_viewed`**: In `features/case/evidence/index.tsx` when a clue modal or card is selected:
   ```ts
   track({ name: 'clue_viewed', properties: { caseId, clueId } });
   ```
3. **`clue_unlocked`**: In `features/case/evidence/index.tsx` or unlock action handler:
   ```ts
   track({ name: 'clue_unlocked', properties: { caseId, clueId, via: 'contradiction' } });
   ```
4. **`board_link_created`**: In `features/case/board/index.tsx` upon creating a connection:
   ```ts
   track({ name: 'board_link_created', properties: { caseId, a, b, valid } });
   ```
5. **`case_submitted`**: In `features/case/theory/index.tsx` when submit button completes:
   ```ts
   track({ name: 'case_submitted', properties: { caseId, correct, score, durationSec } });
   ```
6. **`reveal_viewed`**: In `features/case/reveal/index.tsx` upon screen mount:
   ```ts
   track({ name: 'reveal_viewed', properties: { caseId } });
   ```
7. **`next_case_tapped`**: In `features/case/reveal/index.tsx` when tapping next case:
   ```ts
   track({ name: 'next_case_tapped', properties: { caseId } });
   ```
8. **`challenge_created`, `challenge_opened`, `challenge_completed`, `signup_from_challenge`**: In challenge flow screens / deeplink handlers.
9. **`case_reported`**: In case reporting dialog when player submits feedback.

## 6. Risks / Follow-ups
- **PostHog Native Module in Expo Go**: `posthog-react-native` provides safe JavaScript fallbacks, but full analytics transport requires development builds (`npx expo run:android` / `npx expo run:ios`) or production EAS builds.
- **Sentry Native Crash Reporting**: Requires running `npx sentry-expo-upload-sourcemaps` or Sentry EAS build plugin during production release pipeline.
