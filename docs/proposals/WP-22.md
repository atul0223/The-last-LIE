## 1. Context & Motivation

During WP-22, the progression engine was implemented in `packages/case-engine/src/progression/`.
In accordance with `AGENTS.md` and `WORKBOARD.md`, the shared schema directory (`packages/case-engine/src/schema/**`) was frozen during this active wave.

Consequently, new progression types and Zod schemas were implemented in `packages/case-engine/src/progression/types.ts`.

---

## 2. Proposed Schema Promotion

We propose promoting the following types and schemas into `packages/case-engine/src/schema/progress.ts` (and exporting via `packages/case-engine/src/schema/index.ts`) in the next contract wave:

1. **`DetectiveRankSchema` / `DetectiveRank`**:
   Enum union of `'Trainee' | 'Investigator' | 'Specialist' | 'Senior Detective' | 'Master Detective'`.
2. **`MasteryGateSchema` / `MasteryGate`**:
   Defines `minDifficulty`, `qualifyingSolves`, and `minEvidenceQuality` (default: 0.60).
3. **`RankDefinitionSchema` / `RankDefinition`**:
   Defines rank identity, hierarchy level, name, `xpThreshold`, and `masteryGate`.
4. **`ProgressionConfigSchema` / `ProgressionConfig`**:
   Config schema containing `ranks`, `difficultyMultipliers`, and `replayMultiplier`.
5. **`MasteryCountsSchema` / `MasteryCounts`**:
   Record mapping each difficulty `1 | 2 | 3 | 4 | 5` to integer solve counts.
6. **`PlayerProgressSchema` / `PlayerProgress`**:
   The canonical shape for player progress, matching the `player_progress` database table in `SYSTEM_DESIGN.md` §8.1:
   - `userId?: string`
   - `xp: number`
   - `rank: DetectiveRank`
   - `solvedCount: number`
   - `correctCount: number`
   - `mastery: Record<Difficulty, number>`
   - `solvedCaseIds: string[]`
   - `unlockedDossierIds: string[]`
   - `updatedAt?: string`
7. **`ProgressionEventSchema` / `ProgressionEvent`**:
   Discriminated union for events: `xp_gained`, `rank_up`, `mastery_progress`, `unlock`.

## 3. Architecture Decision: Single Source of Truth for XP

### The Conflict
- In `packages/case-engine/src/scoring/score_submission.ts` (implemented in WP-06), `ScoreResult.xp` is calculated as:
  ```ts
  const difficultyMultiplier = def.difficulty ?? 1;
  const replayFactor = session.mode === 'replay' ? 0.25 : 1.0;
  const xp = Math.max(0, Math.round(score * difficultyMultiplier * replayFactor));
  ```
  This hardcodes the difficulty multiplier directly to `def.difficulty` (linear 1x, 2x, 3x, 4x, 5x) without reference to progression configuration.
- In `SYSTEM_DESIGN.md` §7.3 and PLAN WP-22, progression thresholds and multipliers are configurable (`ProgressionConfig`, backed by `game_config` table).

### Decision Made
1. **`applyResult` in `packages/case-engine/src/progression/apply_result.ts` is the authoritative source of truth for progression XP**:
   - `applyResult` calculates XP as:
     ```ts
     const diffMultiplier = config.difficultyMultipliers[caseMeta.difficulty] ?? 1.0;
     const replayMultiplier = isReplay ? (config.replayMultiplier ?? 0.25) : 1.0;
     const earnedXp = Math.max(0, Math.round(result.score * diffMultiplier * replayMultiplier));
     ```
2. **Preventing Double Multipliers**:
   - XP is calculated from `result.score` (the unscaled raw score), NOT `result.xp`.
   - This guarantees that difficulty and replay multipliers are never applied twice.
3. **Role of `ScoreResult.xp`**:
   - `ScoreResult.xp` serves as a submission-level preview for immediate UI feedback.
   - For authoritative account progression and events, `applyResult` computes the actual awarded XP according to active `ProgressionConfig`.

### Future Recommendation
In a future contract/scoring cleanup wave:
- Either pass optional `ProgressionConfig` into `scoreSubmission`, OR
- Retain `scoreSubmission` as pure score calculation (`result.score` and `result.breakdown`) and deprecate `result.xp` in favor of `applyResult`.
